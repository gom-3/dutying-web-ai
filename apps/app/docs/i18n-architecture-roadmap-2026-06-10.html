지속 개발을 위한 국제화 개편 방향

작성일: 2026-06-10 · 대상: dutying-web/apps/app 중심, Spring 서버 계약 연동 포함

웹·앱·서버 공통 운영 기준: /Users/beomjinkim/swm/docs/i18n-cross-platform-operating-model-2026-06-10.html

결론

앞으로 화면이 계속 추가·변경될 것을 전제로 하면, 국제화의 병목은 번역 자체보다 누락 탐지, 키 소유권, 리뷰 흐름, UI 길이 회귀 검증이다. 따라서 지금의 단일 locale 파일 중심 구조를 feature-owned namespace 구조로 바꾸고, CI에서 누락·미사용·interpolation mismatch·하드코딩·모바일 overflow를 자동으로 막는 방향이 가장 효율적이다.

다만 번역 전문가 검수까지 고려하면 feature-owned locale 파일만 원본으로 두는 방식은 부족하다. 최종 권장 구조는 개발자가 쓰기 좋은 feature별 fragment와 번역가가 대조하기 좋은 중앙 번역 카탈로그를 함께 운영하는 하이브리드 방식이다.

현재 상태 평가

좋은 기반

ko/en/ja 리소스, useTypedTranslation, locale 헤더, 하드코딩 스캐너, 전체 테스트 한국어 고정이 이미 갖춰졌다.

커질수록 생길 문제

locale 파일이 계속 커지면 충돌과 중복이 늘고, 화면 변경자가 번역 키 추가를 놓쳐도 리뷰 전까지 발견하기 어렵다.

가장 큰 리스크

긴 영어/일본어 문구가 새 화면의 버튼, 탭, 모달, 테이블 헤더, 모바일 히어로에서 레이아웃을 깨는 문제다.

중앙 검수의 정확한 범위

UI/UX 변화가 계속 있는 제품에서 모든 문구 변경을 중앙에서 승인하게 만들면 병목이 생긴다. 따라서 중앙 집중화는 승인 프로세스가 아니라 기록, 대조, 용어, 릴리스 품질 관리를 뜻해야 한다.

구분 소유자 운영 방식
화면 microcopy 웹/앱 기능 담당자 PR에서 빠르게 변경한다. 단, 카탈로그와 자동 검증을 반드시 통과한다.
도메인 핵심 용어 중앙 용어집 병동, 신청근무, 확정 근무표처럼 제품 전체에 반복되는 용어는 중앙에서 고정한다.
브랜드/마케팅/온보딩 문구 제품/마케팅 + 번역 검수자 감성, 톤, 국가별 자연스러움이 중요하므로 release 전 검수 대상으로 둔다.
법적/정책/결제/권한 문구 운영/법무/정책 담당 번역보다 정확성이 우선이므로 별도 승인 상태를 둔다.
서버 에러/검증 메시지 서버 계약 + 클라이언트 fallback 서버 messageKey를 표준으로 두고, 플랫폼별 표시 문구는 클라이언트 카탈로그에서 관리한다.

결론적으로 중앙 카탈로그는 UI/UX 실험을 느리게 만드는 게 아니라, 흩어진 변경을 모아 번역 전문가가 나중에 대조·검수할 수 있게 하는 감사 로그이자 품질 게이트로 둔다.

이번 적용 상태

이 문서의 첫 단계로 웹 앱에 카탈로그 기반 생성 파이프라인을 적용했다. 기존 한국어·영어·일본어 런타임 문구를 apps/app/i18n/catalog/messages.csv로 가져오고, apps/app/src/shared/i18n/resources.generated.ts를 생성해 src/i18n.tsx에서 사용하도록 전환했다. 따라서 앞으로 웹 문구 변경은 카탈로그 수정 → 검증 → 웹 export 순서로 관리한다.

명령 역할
pnpm i18n:import-current 기존 src/shared/locales 값을 messages.csv로 초기 이관한다. 반복 실행 시 현재 카탈로그를 덮어쓰므로 마이그레이션 전용으로 사용한다.
pnpm i18n:catalog:check 중복 runtime key, 필수 메타데이터, interpolation mismatch, 서버 메시지 표시 정책 누락을 검사한다.
pnpm i18n:export:web 카탈로그에서 웹 런타임 리소스 resources.generated.ts를 생성한다.
pnpm i18n:review 번역 전문가용 대조 HTML apps/app/i18n/review/i18n-review-board.html을 생성한다.
pnpm i18n:sync-server-errors Spring 서버의 messages_ko/en/ja.properties를 platform=server 행으로 카탈로그에 동기화한다.
pnpm check:i18n 하드코딩 문구 스캔과 카탈로그 품질 검사를 함께 실행한다.

목표 아키텍처

0. 원본은 번역 카탈로그, 코드는 생성물

영속 관리 기준의 source of truth는 코드 파일이 아니라 i18n/catalog/messages.csv 또는 TMS에 둔다. 코드의 ko.ts, en.ts, ja.ts는 이 카탈로그에서 생성하거나, 최소한 양방향 동기화 검증을 거친다. 이렇게 해야 일본어/영어 전문가가 한 화면에서 한국어 원문, 영어, 일본어, 설명, 화면 위치, 길이 제한을 같이 볼 수 있다.

page.member.addNurse,web,page.member.addNurse,page.member,member,button,reviewed,,18,,nurse,빈 팀과 상단 액션 버튼에 사용,/member,MemberPage,,간호사 추가하기,Add nurse,看護師を追加,,2026-06-10

번역 전문가 관점에서는 위와 같은 행 기반 카탈로그가 가장 중요하다. feature별 코드 파일은 개발자에게 편하지만, 언어별 대조·필터링·검수 이력·용어 일관성 확인에는 행 기반 표나 TMS가 훨씬 낫다.

1. Feature-Owned Namespace

번역 리소스는 화면/기능 소유권과 같은 위치에서 관리한다. 예를 들어 회원 화면을 수정하는 개발자는 pages/member/i18n/ko.ts, en.ts, ja.ts만 함께 보면 된다. 

src/shared/i18n/
  core.ts
  locale.ts
  resources.generated.ts
  namespaces.ts
  test-utils.ts

src/pages/member/i18n/
  ko.ts
  en.ts
  ja.ts

src/pages/make-shift/i18n/
  ko.ts
  en.ts
  ja.ts

src/features/shift-editor/i18n/
  ko.ts
  en.ts
  ja.ts

실제 런타임에서는 빌드 전 스크립트가 feature별 리소스를 합쳐 resources.generated.ts를 만든다. 이렇게 하면 파일 충돌을 줄이면서도 i18next 초기화는 단순하게 유지할 수 있다.

즉, 개발 작업 단위는 feature-owned, 번역 검수 단위는 catalog-owned로 분리한다. 둘 중 하나만 선택하면 개발자 또는 번역가 중 한쪽의 운영성이 떨어진다.

2. Namespace 기준

Namespace 소유권 예시
common 공통 UI/상태 저장, 취소, 닫기, 로딩, 빈 상태
term 도메인 용어집 병동, 간호사, 근무표, 신청근무, 오프, 데이/이브닝/나이트
page.member 회원/근무자 관리 화면 테이블 헤더, 모달, drawer, 팀 관리 문구
feature.shiftEditor 근무표 편집 기능 검증 메시지, export 파일명, 툴바, 레이어
server.error API 에러 표시 서버 messageKey와 client fallback 매핑

3. 키 설계 원칙

  • 키는 화면 구조보다 사용자 의미를 기준으로 짓는다. 예: page.member.emptyTeam.addNurse.
  • 단어 조합으로 문장을 만들지 않는다. 일본어/영어 어순이 다르므로 문장은 전체 문장 키로 둔다.
  • 반복되는 도메인 명사는 term에 두되, 문맥이 있는 문장은 화면 namespace에 둔다.
  • 동적 값은 interpolation으로 처리하고, 모든 언어가 같은 interpolation 변수를 갖는지 CI에서 검사한다.
  • 복수/선택/상태 분기는 ICU MessageFormat 또는 i18next plural/context 규칙으로 처리한다.

AST 기반 검증

  • t('...'), i18n.t('...'), <Trans i18nKey="..." />를 AST로 수집한다.
  • 수집된 키가 모든 지원 언어에 존재하는지 확인한다.
  • 번역값의 {{variable}} 목록이 언어별로 같은지 확인한다.
  • 사용되지 않는 키는 warning으로 시작하고, 안정화 후 fail로 전환한다.

타입 전략

현재의 TI18nKey 방식은 충분히 좋은 1차 방어선이다. 다만 키 수가 더 늘면 타입 재귀 비용이 커질 수 있으므로 i18next의 selector API를 중기 과제로 검토한다. i18next 공식 문서는 enableSelector가 큰 리소스에서도 IDE 성능을 개선할 수 있고, v25.4 이후 selector 옵션이 중요해졌다고 안내한다. 

// 현재
t('page.member.title')

// 중기 목표
t($ => $.page.member.title)

단, selector API 전환은 전체 코드 변경량이 크므로 바로 도입하지 않고, locale 분리와 자동 검증을 먼저 끝낸 뒤 codemod 가능한 시점에 진행한다.

UI/UX 안전장치

  • 새 화면 PR은 ko, en, ja, pseudo-locale에서 390px/768px/1280px 스모크를 통과해야 한다.
  • 버튼, 탭, pill, table header, modal title, toast는 긴 문구를 우선 고려한다.
  • 고정 너비 텍스트 컨테이너는 기본적으로 min-width: 0, overflow-wrap: anywhere, 적절한 줄바꿈을 갖는다.
  • 아이콘 버튼은 aria-label도 번역한다. 스크린리더 문구는 visible text와 별도 키를 허용한다.
  • 날짜, 시간, 숫자, 정렬은 직접 문자열 조합 대신 Intl wrapper를 사용한다.

서버 계약 방향

  • 요청은 계속 Accept-Language, X-Service-Region을 보낸다.
  • 계정에는 preferredLanguage, serviceRegion을 저장하고, 로그인 후 client language와 동기화한다.
  • 서버 에러는 message만 믿지 않고 messageKey, messageArgs, locale을 함께 받는 방향으로 고도화한다.
  • 클라이언트는 서버 messageKey를 알면 client locale로 다시 렌더링하고, 모르는 키만 서버 message를 fallback으로 쓴다.
  • 한국어 기존 사용자 보호를 위해 서버 기본값은 ko/KR로 유지한다.

서버 메시지 처리 정책

서버 메시지를 그대로 내려주는 경우는 현실적으로 계속 존재한다. 다만 모두 같은 정책으로 처리하면 안 된다. 메시지 성격별로 책임 위치를 나눠야 웹과 앱이 동시에 안정적으로 관리된다.

메시지 유형 예시 권장 처리
표준 에러 권한 없음, 유효하지 않은 언어, 중복 이메일 서버는 messageKey와 messageArgs를 내려주고, 웹/앱이 자기 카탈로그에서 번역한다.
검증 에러 필드 길이, 형식 오류, 필수 값 누락 필드명과 rule code를 내려준다. 클라이언트가 입력 UI 문맥에 맞게 표시한다.
운영 공지/관리자 작성 메시지 점검 안내, 병원별 공지, 관리자 브로드캐스트 서버 문자열을 그대로 표시할 수 있다. 대신 targetLanguage와 작성 언어를 명시한다.
LLM/외부 서비스 결과 근무표 생성 설명, 외부 API 원문 에러 사용자 노출 전 client/server에서 표준 fallback 문구로 감싼다. 원문은 상세 로그나 debug용으로 분리한다.
법적/정책 문구 약관, 개인정보, 동의 문구 서버 원문 표시를 허용하되 locale별 문서 버전과 승인 상태를 따로 관리한다. 
{
  "code": "DUPLICATE_EMAIL",
  "messageKey": "error.emailAlreadyUsed",
  "messageArgs": {"email": "admin@example.com"},
  "message": "이미 사용 중인 이메일입니다.",
  "locale": "ko-KR",
  "displayPolicy": "CLIENT_TRANSLATE",
  "requestId": "req-123",
  "traceId": "trace-456"
}

핵심은 message를 없애자는 게 아니다. 기존 앱 호환과 긴급 상황을 위해 서버 message는 유지하되, 웹/앱이 같은 품질로 보여줄 수 있는 messageKey 중심 계약을 병행해야 한다.

웹과 앱 동시 관리 모델

웹과 앱을 동시에 관리하려면 하나의 카탈로그에서 모든 플랫폼 문구를 억지로 동일하게 만들면 안 된다. 같은 의미의 메시지를 공통 semantic message로 묶고, 플랫폼별 표현은 별도 surface variant로 둔다. 

messageId: account.delete.confirm
semanticKo: 계정을 삭제하기 전 최종 확인

web.ko: 계정을 삭제할까요?
web.en: Delete this account?
web.ja: アカウントを削除しますか？

app.ko: 계정을 삭제할까요?
app.en: Delete account?
app.ja: アカウントを削除しますか？

serverKey: server.error.accountDeleteFailed
termIds: account, delete
status: reviewed
계층 역할
Global catalog messageId, 의미, 용어, 상태, 검수 이력, 플랫폼별 variant를 관리한다.
Web export i18next namespace/resource로 생성한다.
iOS export Apple String Catalog 또는 .xcstrings로 생성한다.
Android export res/values*/strings.xml, plurals, string-array로 생성한다.
Server export messages_ko.properties, messages_en.properties, messages_ja.properties 또는 messageKey 목록으로 생성한다.

Apple은 String Catalog로 문자열, 복수형, 기기별 variation을 관리하는 방식을 권장하고, Android는 string resource를 앱 문자열의 표준 단위로 사용한다. 따라서 웹/앱 공통 관리는 “런타임 파일을 하나로 통일”하는 것이 아니라, 상위 카탈로그를 공유하고 플랫폼별 native format으로 export하는 방식이 현실적이다.

번역 운영 프로세스

  1. 개발자가 화면을 바꾸면서 source language인 한국어 키를 feature namespace에 추가한다.
  2. pnpm i18n:sync가 중앙 카탈로그에 키를 추가하고 영어/일본어를 TODO 상태로 생성한다.
  3. pnpm i18n:build가 카탈로그에서 feature별 locale fragment와 런타임 resource를 생성한다.
  4. 개발 PR에서는 임시 번역을 허용하되, release branch에서는 TODO가 있으면 fail한다.
  5. 일본어는 병원 현장 용어집을 기준으로 검수한다. 단순 기계 번역을 최종 copy로 병합하지 않는다.
  6. 릴리스 전 주요 화면은 pseudo-locale과 실제 일본어 계정 데이터로 QA한다.

번역 전문가 검수 화면/파일 요건

일본어·영어 전문가가 직접 대조해야 한다면, 코드 diff보다 아래 필드를 가진 검수용 카탈로그가 필수다. CSV/XLSX/HTML 리뷰 보드로 시작하고, 운영 규모가 커지면 TMS 또는 XLIFF export로 확장한다.

필드 필요한 이유
key, namespace, owner 어떤 기능의 문구인지 추적하고 담당자를 찾기 위해 필요하다.
ko, en, ja 번역가가 한 행에서 3개 언어를 직접 대조한다.
description, route, component 문맥 없는 번역을 막는다. 같은 "신청"도 버튼/상태/메뉴에서 표현이 달라질 수 있다.
screenshot 또는 Storybook/Playwright URL 전문가가 실제 UI 폭과 주변 문맥을 보며 자연스러움을 판단할 수 있다.
maxLength, surface 버튼, 탭, 모바일 카드처럼 길이 제한이 있는 문구를 별도로 검수한다.
status, reviewer, updatedAt 임시 번역, 검수 완료, 재검수 필요 상태를 릴리스 기준으로 관리한다.
termIds 병동, 근무표, 신청근무, 확정, 오프 같은 도메인 용어의 일관성을 보장한다.

단계별 실행 계획

단계 기간 작업 완료 기준
Phase 1 1~2일 중앙 카탈로그와 용어집 schema를 만들고 현재 ko/en/ja 리소스를 import한다. 전문가 검수용 CSV/HTML에서 모든 키를 3개 언어로 대조 가능
Phase 2 1일 카탈로그에서 runtime resource를 생성하고 i18n:check, interpolation mismatch, unused key 탐지를 CI에 붙인다. 번역 누락 PR 자동 차단, 현재 테스트 625개 통과, 스캐너 0 유지
Phase 3 2~3일 Playwright locale matrix와 pseudo-locale overflow 검사를 만든다. 핵심 화면 모바일/데스크톱 레이아웃 회귀 자동 탐지
Phase 4 선택 i18next selector API 또는 TMS 연동을 도입한다. 대형 locale에서도 타입/IDE 성능 유지, 번역 검수 플로우 자동화
