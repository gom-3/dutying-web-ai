# 조절 필수·권장 선택 복원 설계

## 원인
웹 4e4d9bb3(2026-10-02)는 드롭다운을 대화형 RULE 강도 질문으로 옮겼다. 이후 semantic 화면(6325e769)의 확인은 서버 planHash에 묶인 조건의 표시·확인만 지원하여 강도 수정 동작을 잇지 않았다. docs/ai-chat-ux-review-2026-10-06.md는 사용자 문장으로 강도를 표시하고 검증된 계획을 임의 변경하지 않는 구조를 명시하지만, 선택권 삭제나 성능 개선의 근거는 없다. 따라서 의도적으로 강도 개념을 폐기한 것이 아니라 새 실행 경로의 편집 기능 누락으로 판단한다.

## 변경
기존 확인 PUT의 선택 필드 modalityOverrides(intentId → HARD/SOFT)를 추가한다. 저장된 PREVIEW_READY 계획의 COUNT만 변경한다. 모든 연결 artifact가 RULE이고 해당 템플릿의 카탈로그가 두 강도를 지원해야 한다. 원본을 복사하여 resolved intent와 그에 연결된 모든 RULE severity만 같은 값으로 바꾼다. 나머지 의미·원문·고정 배정·수치는 유지한다. 최초 검증된 매핑에 대한 일대일 변환이며 새 LLM 호출이나 solver 실행은 없다.

서버는 수정 내역을 기존 plan JSON에 기록하고 새 ID·hash의 미확인 계획을 저장한다. 표·대화·맥락·기존 hash·진행 중 실행을 검사하고, 도메인 규칙 검증을 재사용한다. 확인과 실행은 다음 명시적 사용자 동작에서 진행한다. 기존 확인 요청은 그대로 호환한다. 이 변경은 이번 실행에만 적용하며 대화 상태의 원문은 수정하지 않는다.

웹은 서버가 제공한 modalityEditableIntentIds만 선택 가능하게 한다. 여러 조건의 강도를 로컬에서 바꾼 뒤 한 번에 저장한다. 저장 전에는 실행을 막고 취소로 원복한다. ASSIGN/FORBID는 현재 고정·금지 의미를 유지하며 이유를 표시한다. 과거·실행 중·오래된 계획은 수정 불가다. 서버 미배포 시 강도 편집을 제공하지 않는다.

## 검증
COUNT EXACT의 MIN/MAX artifact 동시 변경, 원본 불변, 지원하지 않는 강도·알 수 없는 ID·비 COUNT 거절, 모델 호출 없음, 새 hash/ID와 재확인, 오래된 요청/진행 중 실행 거절. UI 다중 선택·취소·실패·기존 계획 동작·이번 실행만 적용 문구·좁은 화면을 확인한다. Flyway migration 없음. 개발 DB 접속 없음. 배포 순서: 실행 서버 → Spring → web. 실행 서버는 modalityOverrides 감사 필드를 검증하고, 부분 선택 재검증 시에도 COUNT 강도만 변경을 허용한다. 나머지 의미·artifact 동등성 검증은 그대로 유지한다.

## 검증 결과
웹 관련 테스트 92개, Spring 관련 테스트 49개, 실행 서버 관련 테스트 109개 통과. 웹 타입 검사·프로덕션 빌드·변경 파일 ESLint, 실행 서버 전체 기존 CI 대상 Ruff 및 변경 파일 format 검사 통과. 합성 조건을 사용한 실제 컴포넌트의 375px/1024px 화면에서 가로 넘침 없음, 키보드 화살표로 강도 선택, 미저장 변경 시 실행 차단 확인. 강도 변경 중 모델·해석·계산 호출이 없는 것을 검사했으며 전체 계산 시간의 개선 수치는 측정하지 않았다. 운영 배포는 별도다.
