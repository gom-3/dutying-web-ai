# 자동완성·조절 시나리오와 채팅 실패 안내

## 확인한 차이
기존 Web CI에 컴포넌트·해석·API 회귀 검사는 있었지만, 수간호사 사용 흐름을 한 명령으로 반복하고 결과를 남기는 시나리오 실행 입구와 보고서가 없었다. 실패는 채팅에 표시되어도 일반 회색 말풍선이며, API/엔진 원문이 오류 문구로 전달되는 경로와 이전 대화에서 실패 원인이 빠지는 경로가 남아 있다.

## 수정 계약
- 실패는 AI 채팅 안의 빨간 테두리·옅은 배경·느낌표 상자에 남긴다. 자동완성/조절 구분, 이유, 다음 행동을 순서대로 보여주며 실패 안내 모달을 만들지 않는다.
- 완료된 실패 실행은 재시도 성공, 새 요청, 닫기/재열기, 이전 대화 조회 후에도 남는다. 실패한 표를 적용하거나 완료라고 안내하지 않는다.
- 알려진 실패 원인과 사용 제한을 사용자 문구로 변환한다. 서버/예외 원문, enum, 엔진/솔버/검증 게이트 용어를 표시하지 않는다. 기다릴 시간만 숫자와 단위로 추출해서 안내한다. 응답 유실은 실제 실패/조건 충돌로 단정하지 않는다.
- 검증된 검토용 자동완성 초안과 실제 실패를 구분한다. 다른 작업의 초안+미충족 규칙 안내를 보존한다.
- 새 단축 명령으로 웹 시나리오 검사와 JUnit 보고서를 남긴다. CI의 전체 검사가 같은 시나리오를 자동 실행하고 보고서를 첨부한다. 모의 API/모델 검사, 실제 CP-SAT 검사, 실제 LLM 해석 검사를 구분하여 기록한다.

## 사용 시나리오
| 상황 | 확인할 동작 |
|---|---|
| 자동완성 성공 → 새 요청 → 조절 | 각각의 회차와 원래 결과·비교 버튼 보존 |
| 간호사 1 5일까지 N 없게 | 1~5일 포함, 대상 혼동 없음, 다른 간호사·기간 보존 |
| 1~5일 근무 없애기 | 빈칸/O를 확인하고 답변 후 진행, 임의 실행 없음 |
| 계산 시간 초과 | 채팅 실패 상자·원래 표 유지·같은 조건 재시도 |
| 조건 충돌 / 고정 빈칸 | 이유에 맞는 요청 수정 / 표 확인, 무의미한 재시도 없음 |
| API 통신 실패 / 사용 제한 | 내부 메시지 없이 안내, 제한 시간 보존, 중복 계산 차단 |
| 실패 후 성공 / 재열기 / 새로고침 | 실패 기록과 성공 결과 구분, 원래 표·전후 버전 유지 |
| 검증된 검토용 초안 | 초안 표시와 미충족 조건을 유지, 미검증 결과 적용 차단 |

## 검증 범위
웹 시나리오는 실제 제품 컴포넌트와 합성 표를 사용하고 API·모델 응답을 통제한다. 실제 계산을 했다고 보고하지 않는다. 실제 CP-SAT/해석 검사 결과는 별도로 남기며 실사용 병동/간호사 데이터와 운영 서버를 사용하지 않는다.

## 반복 실행

웹 검사만: `pnpm test:ai-scenarios`

웹 + 로컬 실제 계산/의미 계약 검사: `node scripts/test-ai-scenarios.mjs --engine-repo /path/to/dutying-llm-server`

실패하면 명령은 0이 아닌 종료 코드를 반환한다. 웹 `artifacts/ai-scenarios.xml`, 엔진 `artifacts/ai-engine-scenarios.xml`에 JUnit 결과를 남긴다. Web CI는 전체 검사에 이 시나리오를 포함해 실행하고 `web-test-scenarios` 보고서를 첨부한다. CI에서 별도 서버 저장소나 유료 모델을 호출하지 않는다.

2026-10-08 초기 실행: 웹 사용 시나리오 183개 통과, 의미 계약·실제 CP-SAT를 포함한 엔진 검사 86개 통과. 웹은 모의 API·모델 응답을 사용한다. 실제 LLM과 Spring DB까지 연결한 전체 사용자 여정 검사는 이 수치에 포함하지 않는다.

실제 개발계 모델 해석까지 확인: 로컬 `tools/ai_ux_llm_bridge.py`를 실행한 뒤 위 명령에 `--live-bridge`를 추가한다. 이 옵션은 유료 모델 호출을 명시적으로 켜며 합성 명단의 고정된 3개 요청만 사용한다. 운영·고객 근무표를 저장하거나 실행하지 않는다. 기본 CI는 이 옵션을 사용하지 않는다.

실제 개발계 모델 3건 모두 통과: 간호사 1의 1~5일 N 제외(6,147ms), 대상·기간이 다른 두 요청을 각각 보존(3,006ms), '근무 없애기'의 빈칸/O 확인(2,489ms). 이 수치는 로컬 브리지 왕복을 포함한 이번 3건의 실측이며 전체 요청의 속도 보장이나 p95 목표 달성으로 해석하지 않는다. 결과는 `artifacts/live-ai-scenarios.json`에 요청 ID·상태·판정·시간만 기록한다. Spring DB 저장까지의 전체 통합 성공률은 아직 이 검사 범위 밖이다.

버튼 검수에서 재시도 확인 질문이 이전 실행보다 앞에 출력되는 문제도 재현했다. 재시도 질문을 실패 기록 뒤에 배치하고, 확인 중에는 이전 실패의 재시도 버튼을 숨겨 중복 선택을 막는다. DOM 순서 회귀 검사와 실제 브라우저 클릭으로 확인한다.
