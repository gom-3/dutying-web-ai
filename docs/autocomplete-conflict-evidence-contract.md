# 자동완성 충돌 근거와 사용자 편집 연결

## 구현 전 결정

문제: 월 경계의 고정 배정과 연속 근무 상한으로 필수 휴무가 생기면 일별 인원을 충족하지 못해도 현재는 일반 INFEASIBLE만 반환한다. 결과나 안전 조건을 자동으로 바꾸지 않고 충분한 충돌 증거를 반환한다. 스키마 변경/Flyway migration은 없다.

Python은 기존 생성 도메인과 HARD staffing bound/대상 해석을 재사용한다. HARD 최대 연속 근무 창에서 이미 상한만큼 근무가 강제되면 나머지 편집 칸의 근무 가능성을 제거한다. 이전 달의 연속된 알려진 꼬리만 포함하고, 전부 잠긴 창의 기존 위반은 새 차단으로 만들지 않는다. 가능한 근무 집합에 대한 일별 인원 하한 합과 실제 배정 가능 인원의 차이는 충분한 불가능 증거다. 최대 6개 근무 코드의 부분집합을 검사하여 같은 간호사를 서로 다른 근무의 여유 인원으로 중복 계산하지 않는다. 지원 밖/불명확한 입력에서는 추정 거절하지 않는다.

Python `engineResult.violations`의 `PROPAGATED_STAFFING_CONFLICT`는 date, shiftCodes, required, available, ruleIds, nurses(reason/maximum), fixedAssignments(shiftNurseId/date/shiftCode)를 포함한다. 이 증거는 유일 원인·최소 수정안·안전 대안이라는 주장이 아니다. Spring은 현재 팀 간호사/현재 달과 연결된 전월 날짜/카탈로그/고정 배정 범위를 검증한 DTO만 `failure.conflicts`로 전달하며 이름은 서버의 현재 권한 범위에서 채운다. 임의 내부 문자열이나 범위 밖 ID는 전달하지 않는다.

웹은 충돌 날짜, 필요/가능 인원, 관련 간호사와 고정 배정을 보여준다. 셀 보기 버튼은 현재 편집기의 같은 간호사 ID/날짜/근무를 재확인하고 선택·스크롤·포커스한다. 과거 달 셀은 읽기 전용 근거이며 현재 월 편집 동작과 구분한다. 확인 동작은 근무표/고정 상태/수락 신청을 변경하지 않는다. 편집은 기존 표 편집 기능을 이용한다. 오래된 결과나 다른 달/팀에서는 잘못된 셀로 이동하지 않는다.

회귀: 16명, D4/E4/N3, 1일 고정 휴무5명, 다른 간호사 전월29~31 D/2~3 N/최대5 → 1일 가능10명. 하드룰/전월/고정 상태 변경, 사용자 정의 코드, SOFT, 부분 월, 동일 인원의 중복 자격, 권한 범위, 오래된 UI 결과, 키보드 이동도 검사한다. 개인정보를 저장하지 않는 합성 fixture를 사용하고 외부 모델을 호출하지 않는다.
