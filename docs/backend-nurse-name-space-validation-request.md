# 백엔드 요청: 간호사 이름 공백 허용

## 현재 국제 이름 처리 계약

온보딩·근무자 관리·프로필·가입의 이름은 표시 언어에 따른 한·영·일 문자 제한 없이 처리한다. Unicode 문자·숫자·결합 표시와 하이픈, 가운데점, 아포스트로피, 이니셜의 마침표 및 일반적인 전각/Unicode 표기를 허용한다. 페르시아어 ZWNJ와 인도계 문자 ZWJ는 문자 사이에서 보존한다. 한 글자의 완성된 이름도 허용하며, 미완성 한글 자모·탭/개행·방향 제어 문자·이모지는 계속 막는다.

Unicode 수평 공백은 일반 공백으로 정리한다. 이름과 가나의 전각/반각, 희귀 한자·이체자 선택자는 NFKC로 변환하지 않는다. 입력 중에는 이름 문자를 삭제하지 않고 제출 시 검증하며, 프로필·명단·근무표 붙여넣기의 50 UTF-16 길이 한도에서도 surrogate pair를 분리하지 않는다. 기존 가입/동의/병동 신청 API의 필드와 필수값 계약은 유지한다.

오류 안내의 단일 기준은 CSV 카탈로그의 이름 검증 키 4개이며, 7개 지원 언어를 함께 내보낸다. 로컬 MySQL 8.0 `utf8mb4` 컬럼·연결에서 31개 국제 이름의 INSERT/SELECT 후 UTF-8 HEX가 모두 일치했다. H2 서비스 flush/reload와 실제 컨트롤러·화면 요청도 별도로 확인한다. 운영 DB charset 확인·운영 배포는 이 검증에 포함하지 않는다. 아래 1차 보완 내용과 원 요청은 과거 근거로 보존한다.

최종 로컬 검증: 웹 324개·서버 290개 회귀 통과. 웹 타입 검사, 카탈로그 검사(오류·경고 0), 서버 메시지 소비 회귀도 통과했다. 키보드/붙여넣기·프로필·가입·최종 온보딩 요청과 실제 저장·재조회를 포함한다. 국제 이름을 한 요청에 넣는 화면 회귀의 대기 한도는 입력 행 수 증가에 맞춰 10초로 설정했다. 운영 반영은 별도다.

## 1차 온보딩 Unicode 검증 보완

`dutying-server-ai`와 대조하면 일반 한자·히라가나·가타카나 및 사진의 여섯 이름은 정상이다. 하지만 온보딩은 계정 가입용 검증을 재사용해 전각 영숫자, 반각 가나, 호환 한자와 보충 한자를 거절한다. 반대로 일부 분리 탁점·반탁점은 화면에서 통과해도 서버에서 거절돼 공통 `INVALID_TYPE_VALUE` 문구가 표시될 수 있다.

온보딩의 문자 허용 범위를 명단용 검증에 맞추고 NFC 및 중점·U+3000 정규화를 요청의 두 이름 목록에 동일하게 적용한다. 기존 한글 완성 검증과 제어 문자 차단은 유지한다. 서버는 문자 뒤의 결합 표시·일본어 탁점·반탁점을 허용한다. 전각·반각, 희귀 한자, 이체자 선택자는 지우거나 NFKC로 변환하지 않는다. 50자 제한은 서버 엔티티와 입력의 UTF-16 길이에 맞춘다. 계정 가입 검증, 기존 API 구조와 DB는 변경하지 않는다.

검증 대상은 helper, 온보딩 단계 검증, 최종 `nurseNames[]`·`nurses[].name` 요청, 실제 화면의 완료 동작이다. 사진의 당시 입력 전체·서버 기록은 확보되지 않았으므로 당시 실패 원인을 확정하거나 운영 반영이 끝났다고 표기하지 않는다.

로컬 검증에서 수정 전 웹 138개 중 10개 실패를 재현했고, 수정 후 관련 231개와 `tsc -b`가 통과했다. 화면 테스트는 17종 이름의 편집·완료 요청을 확인하며, 가입·기존 근무자 수정 회귀도 포함한다. 연계 서버는 JSON API 요청·H2 저장 재조회 등 관련 143개가 통과했다. 운영 배포는 하지 않았다.

## 배경

온보딩에서 간호사를 등록한 뒤 병동 생성/근무자 등록 API를 호출할 때, 간호사 이름에 띄어쓰기가 포함되면 백엔드 유효성 검사에서 실패합니다.

현재 프론트 온보딩 기본 이름과 엑셀 파싱 결과에는 `신규 간호사 1`, `Nurse 1`처럼 공백이 포함될 수 있습니다. 실제 사용자도 이름/식별용 별칭에 공백을 입력할 가능성이 있어, 백엔드 이름 검증에서 공백을 허용해 주는 처리가 필요합니다.

## 현재 오류

```json
{
  "code": "INVALID_TYPE_VALUE",
  "message": "파라미터 타입이 올바르지 않습니다.",
  "errors": [
    {
      "field": "name",
      "message": "이름은 한글, 영문, 숫자만 입력 가능합니다."
    }
  ]
}
```

발생 API 예시:

```http
POST /wards/{wardId}/shift-teams/{shiftTeamId}/nurses
```

## 요청 사항

간호사 이름 `name` 검증 규칙에 일반 공백 문자를 허용해 주세요.

권장 규칙:

```regex
^[가-힣A-Za-z0-9 ]{1,20}$
```

권장 처리:

- 앞뒤 공백은 `trim` 처리합니다.
- 이름 중간의 일반 공백은 저장/응답에서 보존합니다.
- 줄바꿈, 탭 등 제어성 whitespace는 허용하지 않습니다.
- 전체가 공백인 값은 기존처럼 invalid 처리합니다.

## 영향 API

아래 API의 `name` 또는 `nurseNames[]` 검증에 동일하게 반영이 필요합니다.

- `POST /wards/{wardId}/shift-teams/{shiftTeamId}/nurses`
- 간호사 수정 API의 `name` 필드
- `POST /wards` 요청의 `shiftTeams[].nurseNames[]`
- 온보딩/병동 생성 후 간호사 seed 과정에서 사용되는 간호사 생성 로직

## 예시

허용되어야 하는 값:

```text
홍 길동
신규 간호사 1
Nurse 1
Kim Nurse 2
```

계속 거부되어야 하는 값:

```text
홍@길동
Nurse_1
   
홍
```

## 완료 기준

- `name: "신규 간호사 1"`로 간호사 생성 시 `400 INVALID_TYPE_VALUE`가 발생하지 않습니다.
- 생성된 간호사 조회 응답에서 이름이 `"신규 간호사 1"`로 유지됩니다.
- `/member` 근무자 관리 화면에서 공백 포함 이름이 그대로 표시됩니다.
- 기존 한글/영문/숫자 이름 검증은 그대로 유지됩니다.

## 프론트 임시 대응

현재 프론트는 백엔드 400을 피하기 위해 저장 직전에 공백을 제거하는 임시 방어 로직을 둘 수 있습니다. 다만 이 방식은 사용자가 입력한 이름을 훼손하므로, 백엔드에서 공백 허용이 반영되면 프론트 정규화 로직은 제거하고 원본 이름을 저장하는 방향이 적절합니다.
