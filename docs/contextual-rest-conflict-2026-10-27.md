# 설정 충돌을 맥락 안에서 해결

사용자가 원한 것은 새 휴무 관리 화면이 아니라, 자동채우기를 막은 실제 설정과 이유를 알고 그 설정을 수정하는 흐름이다. 일반 사이드바 조건 화면의 개인별 휴무 탭을 제거한다. 간호사 상세의 중복 월 목표 입력 폼도 제거하고, 이미 저장된 목표/API는 보존한다.

| Before                              | After                                                                                          | Why                                           |
| ----------------------------------- | ---------------------------------------------------------------------------------------------- | --------------------------------------------- |
| 누구나 휴무 탭에서 목표 관리        | 검증된 충돌이 있을 때만 수정 동작 노출                                                         | 사용자가 새 관리 기능을 배울 필요가 없다      |
| 모든 간호사 선택과 일반 목표 입력   | 충돌에 나온 사람·월·목표·가능 일수만 모달에서 확인                                             | 무엇 때문에 막혔고 무엇을 바꾸는지 보인다     |
| 설정 종류와 무관하게 조건 화면 이동 | 개인 휴무 목표→해당 설정 모달, 근무 가능 여부→기존 근무자 페이지, 일반 규칙→기존 제약조건 모달 | 원인과 수정 장소를 일치시킨다                 |
| 수정 후 조건 메뉴로 복귀            | 같은 실패 안내와 대화·초안·수정 버튼으로 복귀                                                  | 변경한 설정으로 다음 실행을 사용자가 선택한다 |

INFEASIBLE/CONFLICT_REVIEW의 검증된 구조화 근거에서만 설정 수정 맥락을 만든다. 시간 초과/내부 검증 오류/근거 없는 실패는 사용자 설정 문제로 추정하지 않는다. 대상은 현재 명단의 ID 또는 유일한 이름으로만 연결한다. 중복 이름·없는 대상은 첫 번째 사람으로 대체하지 않는다. 여러 사람이 충돌하면 그 사람들만 보여준다.

수정은 명시적 저장에만 반영하며, 기존 근무표/고정/연차 장부는 수정하지 않는다. 저장 후 조건을 다시 읽어 과거 제안을 무효화하고 자동 재실행하지 않는다. DB/API/솔버 변경 없음. 기존 취소·버전 충돌·저장 중 차단·재조회 재시도 처리를 유지한다. develop 반영까지 진행하고 운영 배포는 포함하지 않는다.

검증: 일반 조건에 휴무 탭 없음, 검증된 근거와 수정 대상 일치, OFF/연차 별도 합계·0/null·고정 보존, 다중/중복/없는 대상, 내부 오류와 시간 초과 오진 방지, 저장/취소 후 원래 대화·포커스 복귀, 기존 회원 설정 링크, 두 대화 경로, 데스크톱/모바일 브라우저 확인.

## 구현 확인

- 실제 실패의 검증된 숫자 근거를 실패 상태에 보존하고, 현재 명단에서 대상을 확인한 뒤에만 수정 모달을 연다. 이름이 중복되거나 ID가 없으면 임의의 다른 사람으로 대체하지 않는다.
- 근무 가능 여부 충돌과 대상 식별 실패는 해당 대화의 팀이 선택된 기존 근무자 페이지로 연결한다. 일반 규칙은 기존 제약조건 모달을 연다.
- 휴무 모달은 충돌에 나온 사람만 선택할 수 있다. OFF/연차 값·기존 설정 사용·0일·버전 충돌·중복 저장·닫기 전 초안 보호는 유지한다.
- 저장 후 동일 대화로 복귀하고, 조건을 다시 읽어 기존 실행 미리보기를 무효화한다. 모달을 닫는 동안 다른 편집기를 잠깐 마운트하지 않는다.
- 신규/기존 두 대화 경로, 설정 페이지의 팀 보존, 내부 오류/시간 초과 오진 방지, 회귀 입력, 근무표 불변을 테스트한다. 로컬 합성 명단으로 데스크톱 및 375×812 화면에서 수정·저장·복귀·일반 조건 화면을 확인했다. 실제 계정/API/AI 호출은 사용하지 않았다.

검증 결과: `vitest run src/pages/make-shift src/pages/member` 97개 파일 / 1,220개 통과, 3개 기존 skip. `tsc -b`, 변경 소스 ESLint, `tsc && vite build`, `git diff --check` 통과. 기존 React act 경고 및 번들 크기 경고는 남아 있으며 실패는 없다.
