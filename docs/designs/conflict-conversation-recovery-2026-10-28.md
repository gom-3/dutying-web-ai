# 충돌 후 대화 복구

최신 develop의 충돌 상세·동의 컴포넌트를 재사용한다. 별도 세션의 stale 비교 수정은 복제하지 않는다.

- conflictReview의 설명·규칙·날짜·인원 근거를 실패 기록에도 보존한다. 동의 토큰은 실패 설명에 복제하지 않는다. 상세가 없으면 원인을 확인하지 못했다고 명시한다.
- 충돌 확인에서도 설정 수정·요청 수정·조건 확인 후 다시 채우기를 제공한다. 생성 재시도는 기존 준비 흐름을 사용한다. 동의 후보 적용과 재생성을 구분하고, 만료 토큰 재사용·자동 실행은 금지한다.
- 최신 실행 실패는 안내를 닫아도 확정 버튼을 노출하지 않는다. 정상 성공 후에는 기존 확정 동작을 유지한다. 과거 실패가 새 성공을 막지는 않는다.
- legacy 실패에서도 상세·복구 선택지를 유지한다. 기존 공통 충돌 동의 UI가 포함된 경우 상세 목록 중복은 피한다.
- 검증: 원인 표시, 상세 누락, 만료 후보, 조건 수정 후 재시도, 요청 입력 복원, 실패 후 확정 숨김 및 성공 후 복귀를 집중 회귀로 확인한다. DB/schema 변경 없음.

기존 legacy 충돌 modal은 z-index 200, 사이드바는 1400이었다. 모달을 제거하고 같은 ConstraintConflictReview를 실패 말풍선 안에 렌더한다. 요청 바꾸기는 단순히 사이드바만 여는 대신 입력창을 복원한다. 새 실행 시작 시 이전 pendingConflict를 제거한다.

## 수정 입력에서 자동채우기로 전환

수정 모드에서는 시작 선택지가 사라지므로 입력창 바로 위에 ‘자동채우기로 전환’을 둔다. 클릭은 기존 재생성 선택과 동일하게 준비 단계만 연다. 전환 전에 작성한 미전송 문장은 준비 단계와 취소 이후에도 유지한다. 실행/해석 진행 중에는 전환을 차단하며, 요청 전송·후보 적용·대화 초기화는 하지 않는다. conversation/legacy 공통 버튼과 각각의 회귀로 확인한다.

## 개발계 실제 검증 후 보완

QA ward582/team955의 실제 대화22에서 GENERATE 결과가 새 authoringOutcome 경로의 recovery=revise로 변환되면 confirmationRequired가 없어 재시도 버튼이 숨는 것을 확인했다. 기존 legacy conflictReview의 confirmationRequired만 검사하던 제한을 없애고, 실행 완료된 GENERATE의 review/revise 모두 기존 준비 단계로 돌아갈 수 있게 한다. 접근/쿼터 차단 및 구성원 설정 오류는 그대로 유지한다. 실패 안내·근거·현재 표·고정과 원래 fillPolicy를 유지하며, 자동 실행이나 이전 동의 토큰 재사용은 하지 않는다. QA 조건은 원래 7개로 복구한다.

같은 실패 결과에 SATISFIED 문구가 남아 “조정했어요”라고 표시되는 것도 확인했다. 실제 적용할 결과가 없어 failure로 분류한 경우에는 성공 문구를 재사용하지 않고 기존 “근무표를 바꾸지 못했어요”를 사용한다. 판정/적용/동의 검증은 변경하지 않는다.
