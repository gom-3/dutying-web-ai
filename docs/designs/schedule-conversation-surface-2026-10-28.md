# 자동완성 후 대화로 조절 — 사용자 흐름과 내부 모니터링 분리

2026-10-28. 현재 대화의 최신 설계안. 앞선 비교 화면은 설계 과정의 이력이며, 아래 원칙이 우선한다. 이 문서는 구현 기준이다. 운영 배포와 운영 데이터 변경은 포함하지 않는다.

## 사용자 흐름

사용자는 현재 병동 정보·가능 근무·행 순서·기존 조건·고정/승인 배정을 바탕으로 자동완성하고, 같은 근무표를 보면서 대화로 다듬는다.

`자동완성 → 근무표 확인 → 자연어로 조절 → 짧은 변경 안내·되돌리기 → 기존 저장·확정`

기본 결과 예시:

> 신규간호사 2의 하루짜리 OFF를 줄였어요.
> 두 사람의 4칸이 바뀌었어요.
> 되돌리기 / 작은 좋아요·아쉬워요

요청의 효과와 실제 변경만 짧게 설명한다. 조건별 충족/미충족 표, 위반 변화 요약 카드, 표에서 확인 버튼, 조건 추가·수정·삭제 모드는 기본 대화에서 제거한다. 기존 표의 위반 표시와 기존 조건 설정은 유지한다. 사용자가 조건이나 원인을 물으면 해당 요청에 관련된 내용만 설명한다.

### 사용자와 내부 어드민의 역할

| 내용 | 사용자 | 내부 어드민 |
| --- | --- | --- |
| 생성·조절 결과 | 근무표에서 확인 | 입력·후보·적용 결과를 비교 |
| 무엇을 바꿨는지 | 간단한 문장, 변경 표시, 되돌리기 | 간호사·날짜·근무 전후 전체 목록 |
| 조건별 충족·위반 | 기존 표 표시. 요청하거나 실행을 막을 때 관련 내용만 | 규칙별 전후 측정값·위반 변화·영향 범위를 모두 조회 |
| 기존 문제·새 문제 | 일반 대화마다 목록·요약을 추가하지 않음 | 기존 유지·개선·해결·신규·악화·비교 불가 구분 |
| 해석·실행 실패 | 무엇이 안 됐는지와 다음 행동을 짧게 | 입력부터 실패 단계·모델·검증·반영까지 추적 |
| 고정·대상 확인 | 진행에 꼭 필요한 구체적인 질문만 | 어떤 보호/모호성 판정으로 질문했는지 확인 |
| 만족도 | 결과 하단 작은 평가, 이유는 클릭 시 모달 | 해당 결과와 평가·이유를 연결해 검토 |

### 꼭 필요한 질문과 실제 보호 계약

대상이 모호하거나, 고정된 배정을 바꿔야 하는 등 현재 요청을 진행하기 위해 사용자가 실제 선택해야 하는 때에만 구체적으로 질문한다. 전체 규칙 목록이나 일반적인 충돌 해결 모드로 보내지 않는다.

검증은 유지한다. HARD라는 이름만으로 전부 차단하지 않고, 기존 위반의 유지·개선 때문에 무관한 조절을 막지 않는다. 고정/승인 배정·명시적 근무 불가·명시 보호 계약 등을 일반 동의로 풀지 않는다. 현재 서버가 요구하는 후보 동의를 UI만 제거해 자동 승인하는 방식도 사용하지 않는다. 사용자 흐름을 구현할 때 기존 후보 적용 계약과 어떤 운영 예외를 자동 처리할지 함께 정리해야 하며, 이번 모니터링 이동은 그 권한을 바꾸지 않는다.

### 작고 선택적인 결과 평가

- 자동완성·조절 결과가 실제 초안에 반영된 뒤, 결과마다 작은 좋아요/아쉬워요 아이콘을 둔다.
- 한 번 누르면 평가 완료. 선택한 아이콘과 작은 체크로 표시하며 근무표 확정과 혼동하지 않게 한다.
- 선택 후 작은 ‘이유 남기기’를 제공하고 이 버튼을 눌렀을 때만 모달을 연다. 이유는 선택 입력이다.
- 모달 취소는 평가를 취소하지 않는다. 평가와 이유를 수정할 수 있다.
- 실패·미적용 후보·변경 없는 응답에는 기본 노출하지 않는다. 사용자 의견은 계산·표 반영·저장과 별개다.
- 현재 GENERATE 전용 피드백 검증은 ADJUST 결과도 연결할 수 있도록 구현 단계에서 검토한다.

### OFF·연차

기존 연차 관리·신청근무·팀 공통 휴무 산정을 재사용한다. 잔여 연차가 있다고 AI가 이번 달에 임의 소비하지 않는다. 고정·승인된 연차는 보존하고 초안 편집만으로 장부를 차감하지 않는다. 개인별 월 OFF·연차 수량을 일반 규칙으로 다시 만들거나 새 별도 패널을 추가하지 않는다.

최초 설계 이후 develop에는 개인 월 목표 쓰기·편집 제거가 반영됐다(Spring ce9bcdb7 / Web 273ba8cb). 관련 변경과 운영 데이터 정리는 별도 채팅의 이력이다. 이 설계 작업에서 다시 삭제·배포하지 않는다.

## 내부 모니터링: 기존 실행 상세에 모은다

만들어 둔 조건 검증, 위반 비교, 후보·변경 표, 날짜별 그룹 표시는 내부 어드민에서 재사용한다. 새 독립 대시보드부터 만들지 않고 기존 사용자 흐름 상세(schedule-journeys)를 한 실행의 중심으로 삼는다. 사건(schedule-ai-incidents), 해석·모델 trace, 실행 원장을 이 상세에서 연결한다.

### 무엇이 변한 것인지 구분

자동완성·조절로 보통 변하는 것은 근무표이며, 동일한 조건에 대한 실제 값과 충족 상태가 달라진다. ‘제약조건 변화’라는 말 아래 다음 두 가지를 섞지 않는다.

1. 조건 설정 자체의 변경: 사용자가 최소 인원 3→4명, 특정 사람 근무 금지 등을 실제로 수정한 것. 변경 출처·시각·규칙 버전을 표시한다. AI가 몰래 정책을 바꾼 것처럼 기록하지 않는다.
2. 같은 조건의 결과 변화: 조건은 최대 5일 연속으로 그대로인데 실제 결과가 7→6일로 개선된 것. 또는 일별 인원이 3→2명으로 악화된 것. 규칙과 실제 값을 나눠 비교한다.

조건 버전이 달라졌다면 같은 조건으로 재평가한 근거가 있는지 확인한다. 근거 없이 서로 다른 정책의 결과를 같은 척도로 비교하지 않는다.

### 한 실행에서 보는 내용

| 구역 | 내용 |
| --- | --- |
| 사용자 작업 | 자동완성/조절, 몇 번째 실행인지, 당시 사용자 문장·후속 문맥, 계정·병동·팀·월 |
| 당시 화면 | 실제 표시한 응답·오류·선택지, 입력·선택 상태의 필요한 스냅샷. DOM 텍스트만으로 전체 화면을 복원했다고 주장하지 않음 |
| 입력·설정 | 실행 당시 표, 행 순서, 고정/승인 배정, 가능 근무, 이전 월 근무, 조건·초안 버전 |
| 해석 | 요청을 어떻게 이해했는지, 대상/기간/근무, 일회 목표인지 유지 요청인지, 질문·미지원·해석 실패 |
| 계산·검증 | 후보 존재 여부, 요청 달성/부분 개선/미개선, 검증 범위, 시간·대기·모델 정보, 실제 실패 단계 |
| 조건별 변화 | 조건 이름·대상·기간·설정값·수정 전 실제 값·수정 후 실제 값·변화 분류·근거 |
| 실제 반영 | 후보만 생성/서버 초안 반영/클라이언트 표 적용 보고/사용자 되돌리기/최종 확정 저장을 각각 구분 |
| 사용자 평가 | 해당 결과의 좋아요·아쉬워요, 이유, 평가 시점. 처리 성공률과 만족도를 별개로 봄 |

INTERPRET는 기술 단계다. ‘자동완성 후 첫 조절 요청’이라는 사용자 작업 정보와 별도로 표시해야 한다. 누락된 표시·적용 증거는 확인 불가로 남기며 성공으로 간주하지 않는다.

### 조건별 전후 테이블

| 조건 | 대상·기간 | 설정 | 전 실제 값 | 후 실제 값 | 변화 |
| --- | --- | --- | --- | --- | --- |
| 최대 연속근무 | 가상간호사 A · 같은 기존 구간 | 최대 5일 | 7일 | 6일 | 개선, 여전히 미충족 |
| E 인원 | 11/15 · 같은 대상 그룹 | 최소 3명 | 3명 | 2명 | 신규 부족 |
| 하루짜리 OFF 목표 | 가상간호사 B · 이번 표 | 줄이기 | 3개 | 1개 | 요청 일부 개선 |

숫자는 개념 예시다. 실제 값이 기록·검증됐을 때만 채운다. 첫 생성·빈칸·구 버전 기록 등으로 비교할 수 없으면 ‘비교 불가’로 둔다. 미측정·null·unknown을 0으로 표시하지 않는다. 설정 자체 변경은 별도 이력이며 이 결과 테이블에서 위반 개선으로 포장하지 않는다.

최근 intent-first의 violationDelta(unchanged/improved/resolved/new/worsened), request clauses, validation coverage 및 기존 원본 규칙 검증 결과를 재사용한다. 새/악화만 보는 기본 운영 필터와 전체 조회를 제공하되 전체 원본·증거는 보존한다. 모니터링 화면을 열었다고 solver나 유료 모델을 재실행하지 않는다.

### 최근 9건 사례의 재사용

incident 889의 9건은 D 인원 3일 + E 인원 5일 + 연속근무 1건이다. 기존 규칙별 그룹·날짜별 실제/필요 인원 테이블을 내부 상세로 옮겨 활용한다.

- 서로 다른 날짜·대상은 같은 문장이라는 이유로 제거하지 않는다.
- configured 부족과 내장 zero-coverage가 같은 실제 부족을 중복 보고한 경우만 검증된 동등 키로 묶으며 원본 객체는 보존한다.
- 설명의 6일과 후보의 7일은 전후 비교 증거가 아니므로 6→7 악화로 단정하지 않는다.
- 하한 플래그가 있으면 ‘최소 7일’로 표시하고 전체 연속 구간을 임의로 만들지 않는다.
- 사용자는 매번 이 목록을 검토하지 않는다. 운영자가 실패·품질 저하·사용자 평가를 조사할 때 확인한다.

### 모니터링의 범위

기본은 읽기 전용이다. 일괄 제약 완화, 운영 설정 자동 수정, 어드민에서의 무조건 재실행 기능은 이번 범위에 넣지 않는다. Slack은 사용자 작업·결과·소요시간·필요한 짧은 사유와 동일 실행 상세 링크를 제공한다. 표·원문·개인 식별 정보는 권한 있는 내부 상세에서 다룬다.

이미 저장된 필드부터 활용하고 부족한 정보만 보강한다. 화면을 바꾸는 것으로 과거 누락 기록을 복원할 수 있다고 주장하지 않는다. 당시 입력이 없다면 재현 불가 사유를 표시한다.

## 구현 시 나눌 작업

1. 사용자 사이드바의 불필요한 조건 검토 UI 제거. 입력·재진입·실패 복구·되돌리기와 기존 표의 검증 표시는 보존.
2. 작은 결과 평가를 생성/조절 모두에 연결. 이유 입력은 사용자 클릭으로만 표시.
3. 기존 어드민 실행 상세에서 입력·해석·조건별 전후·사용자 응답·실제 적용·평가를 연결. 기존 검증·그룹 표시를 재사용.
4. UI 정리와 기존 서버의 초안 적용/예외 동의 계약 사이를 정리. 동의 플래그를 자동으로 채우거나 검증을 삭제해 UI를 단순화하지 않음.

이 문서는 제품 설계의 합의 방향이며 애플리케이션 구현 완료 보고가 아니다.


## 구현 범위와 검증 (2026-10-28)

- 사용자 사이드바: 상시 조건 편집·저장 요청 도구, 결과 진단 목록·표 미리보기·별도 신고 설문을 제거한다. 적용 결과의 평가 아이콘은 즉시 저장하고, 이유 입력은 명시적으로 연 모달에서만 전송한다. 실제 예외 후보의 동의 및 보호 계약은 유지한다.
- 기존 실행 상세: 실행별 요청·해석·입력/결과 판본·조건 정의 변화·요청별 before/after·위반 평가 범주·처리 시간·표시/적용/되돌리기/확정·최근 평가를 연결한다. 과거 데이터는 연결·수치가 없으면 확인 불가로 표시한다.
- 대화 해석 및 실행 진입/종료를 기존 journey 저장소에 독립 기록한다. 해석 실패도 원문, 화면 구성 버전/입력 방식(클라이언트 보고), 당시 조건 상태, 판본, revision, 시도/요청 ID, 처리 시간과 안전한 전송 실패 분류를 보존한다. 외부 서버 응답 본문·비밀 오류 문자열은 저장하지 않는다.
- conversation-preview 전송 오류는 INVALID_PARAMETER 400 대신 SCHEDULE_INTERPRET_UNAVAILABLE 503으로 분류한다. 기존 legacy 해석의 null 폴백은 유지한다. 모델·프롬프트·재시도·솔버 제약조건은 변경하지 않는다.
- API 추가 필드: InterpretReq/ExecuteReq.clientContext (선택). 진단용 클라이언트 보고이며 실행 권한이나 제약조건의 정본으로 사용하지 않는다. clientContext는 기존 실행 멱등성 해시 직렬화에서 제외하여 배포 전 재시도 키와 호환된다.
- Flyway migration 없음. 기존 저장소와 어드민 권한을 사용하며 데이터 보정·운영 배포는 포함하지 않는다.
