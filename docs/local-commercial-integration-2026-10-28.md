# 2026-10-28 로컬 상용·병원 관리 변경 통합

## 범위
1. 운영자 요금제 관리와 고객 요금표 연결
2. 병원 관리 화면 개편
3. 개인 관리공간·프로필 개편
4. 병동 생성·병원 연결 동선
5. 병원 최고 관리자 소속 병동 접근
6. 토스 정기결제 준비·실패 복구·인증 복귀 보완
7. AI 대화창에서 근무표 배지와 위반 표시 크기 보정

## 통합 원칙
- 서버 gom-3/dutying-server-ai, 웹 gom-3/dutying-web-ai의 최신 origin/develop에서 시작한다.
- 기존 사용자 작업 폴더, 커밋, 미추적 파일은 변경하지 않는다. 원본 패치·파일 해시를 별도 보관한다.
- 공통 파일의 충돌은 origin/develop 구현을 우선하고 선택한 신규 동작만 현재 구조에 맞춰 추가한다.
- 최근 휴무일 예시 월 이동과 최신 AI 생성·오류 복구 변경을 보존한다.
- 과거 연차/휴무 정책 초안, 배포 검증 브랜치, 화면 캡처 산출물은 반영하지 않는다.

## 하위호환
- 앱 가입·동의·병동 신청의 기존 API 요청/응답과 인가를 유지한다. 새로운 계약이 필요한 경우 별도 버전 API를 사용한다.
- 관리자 조회 응답, 기존 catalog·주문 필드, 유료 고객의 고정 계약·견적을 보존한다. 새 필드는 선택적·추가적으로 제공한다.
- 병원 OWNER의 병동 접근은 현재 소속에 따라 계산하며 실제 병동 OWNER 권한·기존 독립 멤버십을 바꾸지 않는다.
- 결제 응답 불확실성을 재청구 근거로 사용하지 않고 인증 갱신 중 결제 복귀 정보를 보존한다. 공개 가격 대체는 신규 FREE/EVENT 구독에만 적용한다.
- 이미 origin/develop에 있는 V72 결제키 길이 확장과 기존 migration은 수정·재추가하지 않는다. 신규 스키마 변경은 예상하지 않는다.
- DB·실결제·운영 main 배포를 별도로 실행하지 않는다.

## 검증과 반영
- 서버: 상용·결제·병원/병동 인가, API 보안 경계, 기존 계약 및 마이그레이션 회귀와 관리자 JS 테스트, bootJar 빌드를 확인한다.
- 웹: 병원/개인 관리공간, 온보딩, 계정, 결제 복귀·토큰 갱신, 달력 관련 테스트와 타입/린트/빌드를 확인한다.
- 최신 원격과 다시 대조한 뒤 각 저장소의 선택 변경만 develop에 fast-forward push한다. 원격이 추가로 변경되면 충돌 우선 원칙을 적용하고 관련 검증을 반복한다.
- push 결과와 원격 커밋을 확인한다. 실행 서버 배포 완료는 별도 실행 증거가 있을 때만 보고한다.

## 실제 호환 보완
- 관리자 overview의 기존 enabled/plans/subscriptions 필드를 유지하고 정책 편집용 policyPlans/policyEditingEnabled만 추가한다. 새 요금제 저장은 /admin/operations/api/v2/plans/{planCode}에서 제공한다. 관리자 화면은 새 필드를 우선하고 이전 응답은 읽기 전용으로 처리한다.
- 기존 V72는 SQL 주석까지 원격 파일 그대로 보존한다. 새 migration은 추가하지 않는다.
