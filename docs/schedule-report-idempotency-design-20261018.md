# 신고 재시도 멱등성과 결과 안내 회귀 방어

2026-10-18. 선행 웹 PR #85(6a10a514) 위에 별도 브랜치로 작업한다. 원본 checkout과 타 세션 저장소는 변경하지 않는다.

## 근거와 계약 확인

기존 api.report는 POST conversations/{id}/reports에 {operationId,note}를 보내고 {incidentId}를 받는다. #85는 실패한 신고 입력을 보존하지만, 재시도 키가 없다. Spring 기존 report 구현은 매번 report:UUID를 생성하므로 서버 저장 후 응답 유실 시 같은 신고가 중복될 수 있다. 기존 ReportReq는 operationId와 note만 가진다.

백엔드 세션이 optional idempotencyKey 계약을 구현 중이다. 이 시점에는 DTO·검증·호환성 테스트가 미확정이므로 요청 필드 적용을 추측하지 않는다. 독립적인 FE 키 수명과 회귀 테스트부터 작성하고, 백엔드 문서/구현에서 필드와 이전 서버의 unknown-field 처리 근거를 확인한 뒤 연결한다.

## FE 키 수명

한 전송 액션에 UUID를 생성한다. 소유자/권한 모드·병동·팀·월·대화·실행 대상과 trim한 note가 같으면 전송 실패/응답 유실 후 재시도에 같은 키를 사용한다. 키는 서버 접수 ID가 아니며 성공 여부를 증명하지 않는다. 입력 내용(정규화 후)이 바뀌거나 대상이 바뀌면 새 액션으로 취급한다. 성공 후 동일 결과에 새 의견을 보내도 새 키를 쓴다. 전송 중 중복 클릭은 기존 busy guard가 차단한다.

키와 note는 현재 UI 수명 동안 메모리에서만 보유하며 일반 analytics·로그·브라우저 영구 저장소에 넣지 않는다. 새로고침 후 미전송 신고 복구는 이번 범위에 없다. 서버 적용 전에는 키가 무시될 수 있어 중복 저장 방지를 보장하지 않는다. 적용 순서는 웹 #85, 백엔드 신고 멱등성 PR의 검증/적용, 이 후속 웹 PR이다. 이 PR의 기본 대상은 #85 브랜치로 하여 후속 diff를 분리하고 #85 merge 후 develop으로 변경한다.

## APPLIED 안내와 관측 한계

서버 APPLIED는 실행 당시 서버 draft 상태이며 브라우저 현재 표 적용 증거가 아니다. 결과 문구는 실행 시점 작성본 기준임을 알리고 현재 표를 확인한 뒤 별도로 확정하도록 유지한다. 응답 유실 후 복구·새로고침·실행 중 수동 편집·과거 결과 열기에서도 현재 표를 덮어썼다거나 현재 표에 반영됐다고 주장하지 않는지 테스트한다. 생성/조절/표 적용 코드는 변경하지 않는다.

GA schedule_behavior는 원문 없는 행동 enum이고 분모·병동·교대 메타데이터를 수집하지 않는다. 클릭 수는 불만율/전환율이 아니다. 운영 전후 성능/전환 기준선과 서버 멱등성 운영 적용은 미검증이다.

## 검증과 원복

기존 신고/결과/복구 관련 테스트를 기준선으로 실행한다. 키 재사용·내용/대상 변경·성공 후 새 액션·API 기존 호출 호환을 검증하고 UI 회귀를 추가한다. 유료 LLM·운영 신고·운영 replay는 호출하지 않는다. 실패 시 후속 웹 커밋 revert로 #85 상태를 복원하며 서버의 optional 필드는 유지해도 기존 클라이언트가 작동해야 한다. 확인된 계약, 검사 결과와 CI는 후속 HTML 검증 문서에 기록한다.

## 확인된 구현 근거 (2026-10-18 후속 확인)

백엔드 작업 문서 `docs/schedule-report-idempotency-2026-10-18.md` 및 실제 `ReportReq`/controller에서 optional idempotencyKey(1~80자, `[A-Za-z0-9_-]+`), 기존 응답 유지, 누락/null 시 기존 동작을 확인해 FE의 네 번째 선택 인자로 연결했다. UUID는 해당 검증을 만족한다. 서버 note 정규화는 기존 ClientReportSanitizer이며 FE는 기존 trim 전송을 유지한다. 정규화상 같을 수 있는 편집에 새 키를 쓰는 것은 보수적인 새 신고 선택이며 서버와 다른 내용으로 같은 키를 재사용하지 않는다.

이전 서버 호환은 이전 ReportReq 두 필드 구조와 Jackson 사용자 설정 검색(unknown-field 강제 설정/사용자 ObjectMapper 없음), 로컬 캐시의 Spring Web 6.0.9 + Jackson 2.15.0 builder 실행으로 확인했다. 합성 LegacyReport(operationId,note)에 idempotencyKey가 포함된 JSON을 역직렬화해 FAIL_ON_UNKNOWN=false 및 기존 두 값 보존을 확인했다. 이는 해당 버전의 기본 설정 근거이며 운영 인스턴스 설정/배포 확인은 아니다. 신규 서버의 실저장/동시성 검증은 백엔드 PR과 CI의 소유 범위다.

| Before | After | Why |
| --- | --- | --- |
| 신고 실패 뒤 같은 내용으로 재전송해도 요청 연결 키가 없음 | 동일 UI 액션에 UUID를 유지 | 서버 저장 후 응답 유실 시 같은 신고임을 식별 |
| 과거 서버 APPLIED를 로컬 적용으로 오해할 수 있는 회귀 검증 부족 | 응답 유실 복구·remount·수동 편집·과거 보기에서 실행 시점 문구 검증 | 현재 브라우저 상태와 서버 draft 증거를 구분 |

키/원문은 메모리 외로 저장하지 않는다. 의도적 취소는 그 신고 액션을 종료한다. 신고 원문 재입력이나 브라우저 새로고침을 넘나드는 중복 방지는 보장하지 않으며, 스케줄 새로고침 복구와 혼동하지 않는다. GA 코드는 수정하지 않았고 분모를 새로 수집하지 않는다.
