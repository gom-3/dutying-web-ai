변경과 자체 검토

변경 전변경 후판단
실패한 신고를 재전송하면 요청 연결 키가 없음같은 액션·내용·대상은 UUID 재사용서버 저장 후 응답 유실 재시도를 같은 접수로 연결한다.

내용 변경(편집했다 원문으로 돌아오는 경우 포함), 대상 변경, 성공·의도적 취소 후 새 신고는 새 UUID를 사용한다. 공백 trim만 바뀌면 같은 전송 내용이므로 키를 유지한다. 메모리 외에는 키와 note를 저장하지 않는다. 실행 idempotencyKey 및 스케줄 적용 코드는 변경하지 않는다. 전송 성공은 api.report의 성공 응답 후에만 표시한다.

계약과 호환성

기존 api.report 세 인자와 {operationId,note} 본문을 보존하고, 네 번째 선택 인자가 있을 때만 idempotencyKey를 추가한다. 기존 {incidentId} 응답은 같다. 백엔드 작업의 실제 DTO/controller와 docs/schedule-report-idempotency-2026-10-18.md에서 선택 필드(1~80자, A-Z/a-z/0-9/_/-)를 확인했다. UUID는 이 검증을 만족한다. 서버의 권한·범위·내용 바인딩 및 동시성 검증은 백엔드 PR 소유 범위다.

이전 서버 호환 근거: 기존 ReportReq는 operationId/note만 보유하고, 저장소 검색에서 unknown-field 강제 설정이나 사용자 ObjectMapper bean이 없었다. 로컬 Spring Web 6.0.9/Jackson 2.15.0 기본 builder로 합성 LegacyReport를 역직렬화해 FAIL_ON_UNKNOWN=false, LEGACY_DTO_READ=op:synthetic을 확인했다. 이는 로컬 라이브러리 기본 설정 근거이며 운영 설정 확인은 아니다. 이전 서버는 추가 키를 무시해 동작하지만 중복 접수 방지를 보장하지 않는다.

분모·한계·적용 순서

GA 코드는 변경하지 않았다. 행동 enum은 불만율·전환율이 아니며 단계 도달 분모·병동/교대별 메타데이터를 수집하지 않는다. 새로운 성능/전환율 기준선이나 개선을 주장하지 않는다. 운영 요청, 실제 유료 LLM, 운영 analytics 도착, 운영 신고 저장 및 MySQL 동시성은 미검증이다.

미전송 신고의 note/키는 새로고침으로 복원하지 않는다. 의도적 취소 후 재작성은 새 액션이다. 이 경계를 넘나드는 같은 원문의 중복 접수는 이번 구현이 방지한다고 주장하지 않는다. 스케줄 자체의 새로고침 복구와는 별도다.
