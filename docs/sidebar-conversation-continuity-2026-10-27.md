# 사이드바 대화 연속성

사용자가 요청한 대상은 준비 흐름의 단계가 아니라 사이드바 안에 보이는 대화창 전체다. 같은 계정·병동·근무팀·년월에 다시 들어오면 이전 질문, 사용자 응답, 실패/결과, 입력 중이던 요청과 읽던 위치를 이어야 한다.

| Before | After | Why |
| --- | --- | --- |
| 기록 복원 뒤 “이전 대화를 불러왔어요/새 요청”과 시작 안내를 덧붙인다. | 기존 말풍선과 다음 행동만 이어서 표시한다. | 재진입은 새 대화가 아니다. |
| 수정하기를 선택하고 글을 쓰다가 나가면 입력란과 작성 내용이 사라진다. | 선택한 입력 모드와 작성 중인 요청도 근무표별로 유지한다. | 이미 선택하거나 작성한 내용을 반복하지 않는다. |
| 다시 마운트하면 항상 최신 메시지로 이동한다. | 읽던 위치와 최신 대화 따라가기 상태를 복원한다. | 사용자가 읽던 내용을 잃지 않는다. |
| 서버 대화 밖의 오류/안내는 다음 동작이나 재진입에서 사라진다. | 오류·접수 결과는 이력에 남기고 진행 안내는 실제 상태에 맞춰 갱신한다. | 실패 맥락까지 대화창 내용으로 보존한다. |

## 구현 범위

- 기존 서버 대화/브라우저 이력을 활용하고, 대화 문장·입력 상태·스크롤 위치를 함께 유지한다. 재진입을 알리는 가짜 AI 응답이나 반복 시작 안내는 추가하지 않는다.
- 작성 중이던 요청을 복원해도 전송하지 않는다. 과거 실행/확정 버튼의 안전 검증은 유지한다. 실제 실행 상태는 서버 조회를 따른다.
- 사이드바를 접었다 열거나 컴포넌트를 다시 마운트해도 읽던 위치를 유지한다. 새 메시지를 따라가고 있었다면 최신 메시지를 계속 따라간다. 읽던 위치에서 새 메시지가 생기면 기존 최신 대화 이동 버튼을 제공한다.
- 명시적인 새 대화는 입력 내용과 읽던 위치도 초기화한다. 근무표/계정 범위를 섞지 않는다.
- 새 저장소/서버 API/DB 변경과 애니메이션 추가는 필요 없다. 브라우저 보충 기록의 기기 간 동기화 한계는 이전 변경과 같다.

## 검증

실제 부모 화면에서 성공/실패 대화 → 수정 선택 → 요청 작성 → 화면 떠남 → 같은 근무표 재진입을 테스트한다. 메시지 순서와 개수, 작성 내용, 시작 안내의 중복 없음, 자동 요청 없음, 명시적 초기화를 확인한다. 서버 대화에서도 입력 모드와 임시 오류/안내를 유지하는지 확인한다. 스크롤은 닫기/열기와 언마운트/재마운트, 비동기 메시지/이미지 크기 변경, 최신 대화 이동을 검증한다.

- 실패 요청 수정 중 재진입 시 서버에서 해당 요청을 다시 찾아 수정 문맥도 복원한다. 실행/전송은 발생하지 않는다.
- 과거 오류는 같은 제목/내용으로 남기되 `alert`를 다시 발생시키지 않는다. 재시도 성공 뒤에도 과거 오류 때문에 현재 실패처럼 읽히지 않도록 한다.
- “작성 중/처리 상태 미확인”은 대화 응답이 아닌 일시적 진행 상태다. 완료 뒤 오래된 진행 문구를 남기지 않는다. 의견 접수 응답은 이력에 남기며 새 의견 입력란에서 다시 접수한 것으로 표시하지 않는다.
- 합성 데이터만 사용한 실제 브라우저에서 수정 선택 → 입력 → 새로고침 → 닫기/다시 열기를 검증했다. 대화 2개와 작성 내용이 그대로 유지되고 시작 안내/새 요청이 추가되지 않았다.

검증 결과: 자동채우기/수정 UI 31개 파일 511개 테스트 통과. TypeScript, 변경 파일 ESLint/Prettier와 diff 검사 통과. 전체 근무표 테스트에서 확인된 4개 실패는 과거 오류의 alert 재발생과 진행 안내/접수 응답의 보존 정책을 정리한 뒤 해당 31개 파일 전체 재실행으로 해소했다. 나머지 51개 파일은 최초 전체 실행에서 통과했으며 변경 대상이 아니다.
