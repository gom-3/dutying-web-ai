# 수정 완료 후 다음 요청 차단 및 요청 원문 유실

## 확인한 원인

운영 화면에서 첫 수정은 완료됐지만 다음 요청은 로컬 `staleRequest` 검사에서 차단됐다. 서버의 `ScheduleConversation.advance()`는 결과를 적용하며 latestInterpretationId를 비운다. 클라이언트 composer는 이전 ID를 보존하고 있어 새 요청을 오래된 해석 수정으로 오인한다. 이 검사는 해석 API 호출 전이므로 실행 실패 incident도 생기지 않는다.

## 최소 변경

- 서버가 latestInterpretationId를 비웠고 해당 ID의 실행 완료가 확인된 경우 일반 새 요청에서 이전 ID를 해제한다. 서버가 여전히 최신 해석을 유지하면 기간 변경 같은 후속 요청의 문맥을 유지한다. 명시적 요청 수정과 미완료 해석의 최신성 검사는 유지한다.
- 보내기를 누르면 원문을 로컬 대화 기록에 즉시 저장한다. 서버 USER 메시지가 확인되면 서버 기록으로 대체하고 실패/새로고침에도 원문을 보존한다. 근무표와 실행 승인 조건은 변경하지 않는다.
- 해석 전 sync/guard 실패는 기존 대화 reports API에 자동 진단임을 명시해 남긴다. 기존 서버 분류는 USER_REPORT이며 실행 실패로 위장하지 않는다. 단계, 통제된 오류 코드, HTTP 상태만 기록하고 요청 원문, 이름, 토큰, 예외 본문은 보내지 않는다. Sentry에도 정제된 진단만 남긴다. 진단 전송은 제한 시간과 무토스트/무리다이렉트 설정으로 요청 UI를 방해하지 않는다.
- 해석/이력 조회 실패는 Sentry로 분리해 기록한다. 서버 해석 실패의 기존 incident 경로를 중복 생성하지 않는다.

## 검증

완료 후 연속 요청, 오래된 미완료 해석 차단, 응답 대기 중 원문 노출, 실패 후 재마운트, 서버 메시지 중복 제거, 진단 전송 실패와 민감 내용 제외를 결정적 로컬 테스트로 확인한다. Flyway migration 없음. 실제 사용자 요청 재전송 및 운영 근무표 변경은 하지 않는다.
