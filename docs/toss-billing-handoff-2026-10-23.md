# Plus 정기결제 프런트엔드 로컬 전달본

이 변경은 `gom-3/dutying-web-ai`의 `origin/develop` 커밋 `b5b4093b0b4e41514fb84f99a10cf6947d25352f`에서 분리했다. 병원 관리·가입·프로필·근무표 화면의 기존 미커밋 변경은 포함하지 않았다. 로컬 브랜치는 `codex/toss-billing-handoff-web`이다.

## 변경 범위

- 공개 상품 안내는 서버가 게시한 Plus 금액·기본 인원·제공량을 사용한다. 정책이 없으면 임의 가격을 만들지 않고, 가격이 있어도 `ready:false`이면 신청 링크를 열지 않는다.
- 신규 병동 Plus 구독의 FREE/EVENT 계정은 전체 카탈로그를 불러오지 못해도 검증된 공개 Plus 상품이 있으면 해당 가격·기본 인원을 표시하고 서버의 정확한 견적을 요청할 수 있다. 기존 유료 계약 정책이 우선하며, 공개 상품이 `ready:false`이면 동의·본인 확인을 마쳐도 카드 등록을 열지 않는다. dev에서 관찰한 요약 가격 `—`와 정상 견적의 실제 원인은 카탈로그 응답 확인 전까지 미확정이다.
- 상품 이미지, 구독 주기·자동 갱신·해지·환불 안내와 공개 사업자정보를 유지한다. 승인된 사업자등록번호는 **319-05-02789**이다. `VITE_SELLER_REGISTRATION_NUMBER` 빌드 설정이 있으면 소스 기본값보다 우선하므로 운영자가 이 값을 확인해야 한다.
- 카드 등록 전 동의·이메일 본인 확인·유효한 서버 견적을 요구한다. 깨진 견적과 만료된 견적은 결제를 열지 않는다. 기존 유료 계약의 인원·요금 정책을 새 카탈로그 값으로 덮어쓰지 않는다.
- 토스 SDK 로드는 공유하고 실패·15초 지연 후 재시도할 수 있다. SDK를 읽지 못하면 카드 등록 주문을 만들지 않는다.
- 인증 복귀의 `authKey`·`customerKey`·등록 식별자는 앱 초기화 전에 URL에서 제거하고 메모리에만 둔다. 새로고침 뒤에는 주문번호로 상태를 재조회하며 인증 정보 없이 새 청구를 시도하지 않는다.
- 토스 복귀 중 access token이 만료되면 같은 문서에서 쿠키로 세션을 갱신하고 원 요청을 한 번만 재시도한다. 동시 요청은 갱신을 공유하고, 갱신 후 도착한 이전 401은 새 토큰을 사용한다. 새로고침 페이지로 이동하지 않아 메모리의 카드 인증 정보를 보존한다. 갱신 실패 시 현재 화면의 재시도·로그아웃 동작을 이용하며, 다른 계정으로 전환하거나 화면을 나간 뒤 도착한 갱신 결과는 적용하지 않는다.
- 카드 인증만으로 구독 완료를 표시하지 않는다. 사용자가 첫 청구를 확인하고 서버가 `APPLIED`를 반환한 경우 완료를 표시한다. 처리 중·불명·실패 주문의 새 청구와 중복 클릭을 막는다.
- 이메일 인증 결과는 서버 만료시각과 10분 중 이른 시각에 지운다. 새 인증번호 요청 시 이전 인증 결과를 지운다.

토스 시크릿 키·빌링키·카드번호·CVC를 프런트엔드에 추가하지 않았다. 실제 키나 `.env` 파일을 읽거나 전달본으로 복사하지 않았다.

## 로컬 검증

공개 페이지·상용 기능·SDK·결제 복귀·이메일 인증 및 기존 로그인·세션 갱신 회귀 테스트를 한 번에 실행해 160개가 통과했다. 이 중 14개는 결제 복귀의 만료 토큰·갱신 실패·동시 요청·로그아웃 및 계정 전환을, 추가 5개는 카탈로그 실패 시 공개 Plus 정책 활용·잘못된 공개 응답 거절·결제 준비 제한을 검증한다. 기존 유료 계약 우선 테스트도 유지했다. 공개 사전 점검기 계약 테스트 6개도 통과했다. 타입 검사와 프로덕션 빌드도 통과했다. 새 모듈·공개 페이지·수정한 인증 연결부 범위의 ESLint를 확인했다. 기존 공용 파일의 스타일 진단은 별도 manifest에 기준 브랜치와 비교해 기록한다.

의존성 패키지 저장소를 재사용하되 worktree의 `node_modules`와 Vite 캐시는 분리했다. 빌드용 랜딩 SSR 캐시도 개발 서버 캐시와 분리한다. 현재 실행 중인 개발 서버에 접근하거나 재시작하지 않았다.

이 테스트는 가상 PG 응답으로 코드 동작을 검증한 결과다. 실제 TEST 카드 등록·승인·갱신·해지·환불 거래나 심사 제출 증빙은 아니다.

## 운영자에게 남은 확인

1. 별도 서버 전달본과 함께 API 호환성을 검토하고 배포 순서를 정한다. 이 변경의 `subscriptionSummary`는 선택 필드여서 기존 주문 응답을 허용한다.
2. 실제 빌드에서 사업자등록번호 **319-05-02789**가 표시되는지 `/pricing`, `/refund`, `/subscription-terms`를 확인한다.
3. 서버의 게시 정책과 결제 준비 사유를 확인한다. 준비되지 않은 `ready:false`를 프런트에서 우회하지 않는다.
4. `scripts/verify-toss-review.py --web https://dev.dutying.ai --api https://dev.api.dutying.ai --require-ready`를 실행하고, 브라우저에서 실제 상품·약관·사업자정보·로그인 후 결제 흐름을 별도로 확인한다. 이 스크립트의 HTML 통과만으로 화면 내용·배포 커밋을 검증했다고 판단하지 않는다.
5. 심사용 테스트 계정과 실제 TEST PG 거래로 성공·취소·불확실 결과·해지·환불을 확인한다. URL과 PC 시각이 함께 보이는 실제 화면을 캡처하고 인증정보·카드정보·개인정보를 가린다.

DB 적용, CI/CD 설정·실행, 원격 push·PR·배포, 실제 TEST PG 거래, 토스 제출·메일 발송은 이 로컬 전달 작업에서 수행하지 않았다.
