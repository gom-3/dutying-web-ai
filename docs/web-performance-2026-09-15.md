# 웹 성능 최적화 — 2026-09-15

## 범위

메인 웹 앱의 코드 로딩, 반복 계산, 렌더링, 중복 조회를 개선했다. DB, 스키마, 서버 API 계약, 패키지 버전은 변경하지 않았다. 작업 시작 시 존재하던 랜딩 렌더링·호스팅 변경은 보존했다.

## 적용 내용

- **근무표 만들기:** 5개 단계를 각각 지연 로딩한다. 선택한 단계가 준비될 때까지 화면 내부에 로딩 상태를 표시하고 해당 단계의 이동 버튼도 함께 대기시킨다.
- **파일 기능:** 프로필·가입 화면의 사진 압축, 근무표 이미지 내보내기, 업로드한 XLSX 보정용 ZIP 처리를 실제 사용 시점에 로드한다. 기존 압축 옵션, 파일 처리, 오류 안내는 유지한다.
- **근무표 일별 합계:** 근무유형마다 전체 근무자를 다시 검색하던 계산을 한 번의 순회로 바꾸었다. 근무표 내용이 같으면 계산 결과를 재사용하고, 선택 위치와 색상 설정도 필요한 값만 구독한다.
- **공휴일:** 국가별 달력 객체와 국가·연도별 계산 결과를 재사용한다. 1~12월을 차례로 조회할 때 연간 공휴일 계산은 13회에서 2회로 감소한다. 1월의 전년도 연휴 처리도 유지한다. 캐시는 연도 24개와 월 288개로 제한하고, 공휴일이 결과에 반영되지 않는 설정에서는 계산을 생략한다.
- **반응형 메뉴:** 화면 너비가 1280px 또는 1536px 기준을 넘을 때 상태를 갱신한다. 같은 너비 구간에서 매 픽셀마다 레이아웃 상태가 바뀌는 것을 줄인다.
- **병동톡:** 연결된 근무자 수를 표시할 때 다른 화면과 팀 목록 조회 캐시를 공유한다. 30초 이내 데이터가 있으면 추가 요청을 생략하고, 공통 캐시 갱신은 즉시 반영한다.

## 빌드 측정

동일한 로컬 환경에서 작업 직전과 최종 `pnpm build`를 비교했다. 각 화면 진입 모듈과 **정적으로 필요한 공통 JavaScript 의존성**을 중복 없이 합산했다. 지연 로딩 코드는 실제로 해당 기능을 열 때 추가로 다운로드된다. KB는 1,000바이트 기준이며, gzip은 파일별 Node.js `gzipSync` 결과의 합이다.

| 화면 | 변경 전 gzip | 변경 후 gzip | 감소 |
| --- | ---: | ---: | ---: |
| 근무표 만들기 | 1,045.5 KB | 616.9 KB | 41.0% |
| 프로필 | 534.8 KB | 515.3 KB | 3.6% |
| 가입 | 597.1 KB | 576.3 KB | 3.5% |

근무표 만들기의 압축 전 JavaScript도 4,092.6 KB에서 2,050.5 KB로 줄었다. 화면별 수치는 공통 의존성이 겹치므로 서로 더하지 않는다. 배포 환경에서의 로딩 시간이나 실제 사용자 응답 속도를 측정한 수치는 아니다.

최종 Vite manifest에서 근무표의 5개 단계와 `browser-image-compression`, `html-to-image`, `jszip`이 모두 동적 진입점으로 분리된 것을 확인했다.

## 검증

- `pnpm build`: TypeScript 검사 및 운영 빌드 통과.
- 변경한 TypeScript/TSX 파일 15개에 대한 ESLint 검사 통과.
- `pnpm verify:seo`: 웹 정적 경로 34개, 문서 페이지 3개 검증 통과.
- `pnpm --dir apps/app exec vitest run --maxWorkers=4`: **1,477개 통과, 3개 건너뜀, 기존 호스팅 검사 2개 실패**.
- 추가 검증: 합계 계산의 기존 알고리즘과 결과 일치, 공휴일 계산 재사용·생략, 병동톡 캐시 재사용·갱신, 단계 로딩 중 이동 버튼 대기.

남은 2개 실패는 `src/app/__tests__/hosting-config.test.ts`가 재작성 목적지 `/`를 기대하지만 작업 전에 이미 변경되어 있던 Cloudflare/Vercel 설정은 `/app-shell`을 사용하기 때문이다. 이번 최적화에서는 해당 설정이나 검사를 수정하지 않았다. 최초 병렬 전체 실행에서 발생한 랜딩 프로필 표시 테스트의 시간 초과는 개별 재실행과 최종 전체 실행 모두 통과했다.
